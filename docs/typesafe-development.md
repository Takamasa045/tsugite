# 継手でのTypeSafeの使い分け

Jevへの質問を設計・修正するときや、意味による分類・選択を使う機能を開発するときの入口。動画制作の手順は制作Skill、Fast Editの仕様は [fast-edit.md](fast-edit.md) を参照する。

## 開発用Skillと実行経路

`typesafe-ai` は開発エージェント向けの設計ガイドであり、Jevへの接続や編集エンジンを置き換えない。エージェントのスキル一覧にある同名Skillを読み、必要な公式資料だけ参照する。未導入の環境では [公式Skill](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md) を参照できる。制作の実行時依存としてインストールを要求しない。

既存Fast Editは、ローカル解析 → 区間分割 → 既存Jev MCPの `jev_ask` → 厳密な判定検証 → Manifest/EDLへの変換という経路を維持する。Codex等の逐次推論をこの経路へ挿入しない。レンダリングと人間の制作Gateは既存手順に従う。Skillの推奨は外部推論・別の接続先・課金・Gate承認の許可を追加しない。

## 処理の担当

| 処理 | 担当 |
| --- | --- |
| 文字列検索・件数・時刻計算・形式検証 | 通常のコード。開発時の大きなファイルの読み取りには、利用可能ならctxfilter |
| 意味による分類・候補選択・評価 | 既存Jev MCP。少量の単純作業にも毎回呼ぶルールにはしない |
| 開発時の大量JSONLの関連判定 | 利用可能なctxfilter-jev。対象・送信内容の許可範囲を守る。Fast Editの依存には追加しない |
| 設計・実装・原因調査・最終検証 | Codex等の開発エージェントと通常の検査コマンド |

## 質問の設計と確認

- 判断対象のstateと、区別できる候補・質問を定義する。同じstateに対する独立した質問はまとめる。依存する質問は先行結果が必要な段階で実行する。
- 文脈不足や候補外を扱う。既存Fast Editでは欠落・未知の選択肢・低信頼の結果を拒否する契約を維持し、成功させるために候補や信頼度の条件を緩めない。
- 信頼度を正答率や実行許可として扱わない。具体的な入力と期待する分類、曖昧な入力、欠落・不正な応答を確認する。
- 新しい質問や機能を試す場合は、実入力・応答・期待値・使用量・所要時間を残す。外部推論は承認された非機密入力と既存接続で行う。fixture検証と実推論の結果は区別する。
- 節約を評価する場合は同じ仕事・品質条件で比較する。Codex側とJev側の使用量、呼び出し回数、全体所要時間、見落としを分けて記録する。文字数・返却バイト数だけでトークン削減率を断定しない。

変更時の検査は [開発・検証と作業場所](development-workflow.md) に従う。このガイドの追加だけでは質問・モデル・実行設定は変わらず、性能改善や削減率を達成したことにはならない。
